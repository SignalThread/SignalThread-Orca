# Account Selection Flow Bug Fix

**Date:** 2026-01-26  
**Status:** ✅ FIXED

---

## 🐛 Bug Report

### Symptoms
1. After selecting "Acme Coffee" on `/login`, user lands on `/app?account=acme-coffee`
2. `/app` page fails to load account data
3. `/api/app/account?account=acme-coffee` returns "Account not found"
4. Prisma Studio shows account exists with slug `acme-coffee`
5. Seed data is present (events, responses, answers)

### Root Cause
**The API was querying by `id` instead of `slug`**

```typescript
// ❌ WRONG (before fix)
const account = await prisma.account.findUnique({
  where: { id: accountSlug },  // accountSlug is "acme-coffee", but id is a cuid
})

// ✅ CORRECT (after fix)
const account = await prisma.account.findUnique({
  where: { slug: accountSlug },  // query by slug field
})
```

**Why this happened:**
- When removing cookie auth and switching to query params, the where clause was updated to use `accountSlug` variable
- But forgot to change the field from `id` to `slug`
- Database accounts have:
  - `id`: auto-generated cuid (e.g., `cmkurqsgy0000mmu7psncqsrd`)
  - `slug`: human-readable identifier (e.g., `acme-coffee`)
- Query param uses slug, but API was looking up by id

### 1. Account API Route (`app/api/app/account/route.ts`)

**Changed:**
```typescript

  where: { slug: accountSlug },  // Changed from id to slug
  // ... rest of query

```

**Impact:**
- ✅ `/api/app/account?account=acme-coffee` now works
- ✅ Returns correct account data with locations and events
- ✅ Account isolation validated

---

### 2. Event Analysis API Route (`app/api/app/events/[eventId]/analysis/route.ts`)

**Before:**
```typescript
const accountId = request.headers.get('x-account-id')  // From old middleware
```

**After:**
```typescript
const { searchParams } = new URL(request.url)
const accountSlug = searchParams.get('account')

const account = await prisma.account.findUnique({
  where: { slug: accountSlug },
  select: { id: true },
})

// Then verify event belongs to account.id
```

**Impact:**
- ✅ Event analysis endpoint now uses query param instead of middleware header
- ✅ Validates event belongs to requested account
- ✅ Returns "Event not found or access denied" for cross-account access attempts

---

### 3. Event Dashboard Page (`app/app/events/[eventId]/page.tsx`)

**Changed:**
```typescript

// ✅ Added account validation
if (!accountSlug) {
  setError('No account specified')
  setLoading(false)
  return
}

// ✅ Added accountSlug to useEffect dependencies
useEffect(() => {
  fetchData()
}, [eventId, accountSlug])
```

**Impact:**
- ✅ Event dashboard loads correctly
- ✅ Shows error if account param missing
- ✅ Recompute button works correctly

## 🎓 Lessons Learned

1. **Field vs Value Mismatch**
   - When refactoring, always verify the query field matches the data type
   - `id` field contains cuids, `slug` field contains human-readable strings

2. **Migration from Middleware to Query Params**
   - Removed middleware that set `x-account-id` header
   - Updated all API routes to read from query params
   - But forgot to update the database query field

3. **Testing is Critical**
   - The build passed, but runtime behavior was broken
   - End-to-end testing would have caught this immediately
   - Always test the full flow, not just compilation

4. **Database Schema Awareness**
   - Prisma schema shows `id` and `slug` are different fields
   - Account has both for flexibility (internal vs public identifiers)
   - Query the right field for the right use case
