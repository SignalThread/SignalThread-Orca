# User Table Investigation & Production Fix

## 🔍 FINDINGS

### Architecture Verification

**Authentication:** Supabase (`auth.users`)  
**Authorization:** App-managed `public.User` table

### Schema Analysis

**File:** `prisma/schema.prisma` (lines 355-368)

```prisma
model User {
  id        String    @id // Supabase user.id (uuid)
  email     String    @unique
  role      UserRole  @default(ADMIN)
  accountId String?   // NULL = SUPER_ADMIN, set = account-scoped
  isActive  Boolean   @default(true)
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  account   Account?  @relation(fields: [accountId], references: [id], onDelete: Cascade)
}

enum UserRole {
  SUPER_ADMIN  // Full system access
  ADMIN        // Account-level admin
  MANAGER      // Location-level manager
  VIEWER       // Read-only access
}
```

**Purpose:**
- Bridge between Supabase auth.users (authentication) and app authorization
- `id` field matches Supabase user.id (UUID)
- Stores `role` for authorization (SUPER_ADMIN, ADMIN, etc.)
- Links to Account via `accountId` for multi-tenant scoping
- NOT a replacement for Supabase - it's an authorization layer

## ✅ CONCLUSION

**The codebase IS intended to use a Prisma-managed `public.User` table.**

**Why it's needed:**
1. **Authorization:** Stores user roles (SUPER_ADMIN, ADMIN, etc.)
2. **Multi-tenancy:** Links users to accounts via accountId
3. **Supabase Bridge:** Maps Supabase auth.users to app context
4. **Access Control:** Required for route guards and permissions

**This is NOT a duplicate of Supabase auth.users:**
- Supabase handles authentication (login, sessions)
- Prisma User handles authorization (roles, account access)
