# Orca OS Integration Boundaries

Updated: 2026-08-11. This document describes only integrations that exist in the repository. The event registration connection tables are a provider-neutral seam; no registration-provider adapter or live synchronization is implemented or advertised.

## Boundary matrix

| Boundary | System of record | Direction and allowed data | Conflict resolution | Retry, replay, and concurrency | Ownership and configuration | Retention and deletion |
|---|---|---|---|---|---|---|
| PostgreSQL / Prisma | Orca OS is canonical for organizations, access, events, operational records, readiness inputs, audit history, publications, and export history. | Server services read/write through event- and organization-scoped queries. Browser code uses authenticated APIs and never Prisma. | Transaction constraints, versions/CAS, unique keys, advisory locks for contested ordering/identity operations, and domain-specific deterministic rules win. | Mutations use transactions and operation-specific idempotency keys or unique constraints. Predictable 400/403/404/409 errors are returned at API boundaries. | Application deployment owns `DATABASE_URL`; it is server-only. | Foreign keys and documented soft-delete/archive rules govern application data. Migrations are forward-only and additive in this release. |
| Supabase Auth | Supabase owns authentication identity/session state. Orca OS owns the application user, active organization, memberships, event roles, and all authorization decisions. | Verified identity flows into server request resolution; application authorization never flows from browser claims alone. | A valid Supabase identity without a valid scoped Orca user/membership is denied or sent through explicit provisioning/organization selection. | Session refresh is handled by Supabase; request resolution is repeatable and does not create broader membership. | Deployment owns Supabase URL/keys; admin credentials stay in server-only modules. | Supabase identity deletion does not silently delete operational history. Application-user lifecycle must preserve required historical actor snapshots and follow organization retention policy. |
| Cloudflare R2 / S3 API | Orca OS database records own document/file metadata, event scope, versions, state, and object keys. R2 owns bytes only. | Server issues bounded presigned operations; browser transfers bytes only to the exact signed object key. Server fetches source files for authorized processing. | Database version/status is authoritative. An orphaned object is never treated as an active document; a missing object produces a recoverable storage error rather than fabricated content. | Presign/finalize separates transfer from canonical activation. Repeating finalize follows record/version guards. External object cleanup is explicit and must not be inferred from a database cascade. | Deployment owns endpoint, bucket, access key and secret. Credentials never enter client bundles or logs. | Database deletion/archive follows domain policy. Remote object deletion requires the corresponding explicit storage lifecycle; retention jobs must reconcile orphan records/objects without exposing cross-event keys. |
| SendGrid | Orca OS owns drafts, approvals, schedules, recipients, suppression, and campaign/audit state. SendGrid owns transport delivery. | Approved recipient-scoped messages flow out; signed delivery/engagement/suppression events flow in through the sessionless webhook. | Orca approval/suppression rules decide send eligibility. Provider events may advance transport milestones but do not rewrite message content, recipients, or permissions. | Recipient-scoped provider/custom IDs and webhook event IDs provide deduplication; stable fallback IDs handle missing provider event IDs. Failed sends remain explicit and can be retried through the canonical service. Scheduled sends are claimed through repository service logic. | Deployment owns API key, sender identity, and webhook verification key/secret. No browser configuration surface exposes them. | Marketing history and suppression records follow application retention. Provider-side deletion does not erase Orca audit history; content/logging policies exclude secrets and unnecessary bodies. |
| OpenAI | Orca OS canonical records and deterministic readiness remain authoritative. Model output is an unverified proposal only. | Bounded menu images/text or room-planning inputs flow out from authenticated server routes; structured proposals flow back for validation and planner review. Executive Briefing remains deterministic and does not call a model. | Schema validation, conservative allergen rules, deterministic geometry/business rules, and explicit planner verification override any model suggestion. Missing credentials return a truthful 503/fallback state. | Calls are request-scoped. Retrying does not itself verify or publish data; persistence services apply their own idempotency/version controls. | Deployment owns `OPENAI_API_KEY` and model selection. Browser code receives neither credentials nor raw provider errors. | The application stores only domain records/proposals needed by the workflow, not provider credentials. Deleting source/application records follows their domain lifecycle; provider retention is controlled by the deployment’s provider agreement. |
| Public agenda publication | The immutable `SessionAgendaPublication` snapshot is the public source of truth; mutable internal session/show-flow rows are not served directly. | Explicitly published allowlisted fields flow outward through the public event agenda route and public export projection. | Latest publication version wins deterministically. Internal edits are invisible until a new publish action. | Publication versions and transactional publish logic make replay deterministic. Public reads are cache-safe and return a non-sensitive empty projection on lookup failure. | Event editors own publish actions. Public readers have no write path. | Publication history is retained for version/audit needs and cascades with the owning event/session according to schema policy. Internal notes, person-level sensitive data, and unverified claims are excluded. |
| Provider-neutral registration seam | Orca OS owns local attendee/directory records and connection/identity mappings. No external provider is currently a source of truth because no adapter is registered. | Today: authenticated event-scoped configuration records and internal identity mapping only. No provider network read/write or live update channel exists. | Capability flags, never provider names, determine whether future records would be read-only or writeback-capable. External identity conflicts return 409; cross-event related IDs return 404. | Event+provider and external-identity unique keys make operations idempotent. Identity linking uses an event/key advisory transaction lock plus atomic upsert. | Event editors own connection records; deployment code must register any future adapter. No speculative OAuth/configuration UI exists. | Connections and mappings cascade with the owning event. Disconnecting records status and Activity history; it does not silently delete attendees or directory people. |

## Shared rule ownership

- Safety and suitability: `web/lib/fnb-compatibility.ts` and menu safety services; missing evidence never implies safety.
- Timing/conflicts: canonical Matrix/session conflict utilities and event timezone/date-only contracts.
- Financials: exact-money F&B calculation and budget reconciliation services; no floating-point currency source of truth.
- Readiness: `web/lib/event-readiness.ts` and its deterministic reason codes; AI only explains that output.
- Exports/privacy: `web/lib/operational-export.ts` and `web/lib/operational-export-service.ts` explicit recipient allowlists; database records are never spread into projections.
- Authorization: `web/lib/event-access.ts` and route request-user resolution; every related object is re-checked against the owning event.

## Live updates decision

No new live-update transport is added. The repository has no shared authenticated subscription architecture, and current operational writes already use explicit refresh/retry, version conflicts, and deterministic reloads. Introducing polling, sockets, or database subscriptions solely for this prompt would add a second consistency path without evidence of a concrete workflow need. Contested mutations remain protected by transactions, CAS, unique constraints, and advisory locks.

## Logging and secrets

API logging records route context and handled error class/code, not credentials, presigned URLs, message bodies, person-level medical/dietary data, or full provider payloads. Client-bound modules may use only `NEXT_PUBLIC_*` configuration; Prisma, admin clients, R2/SendGrid/OpenAI credentials, and server environment access stay behind server-only imports and API routes.
